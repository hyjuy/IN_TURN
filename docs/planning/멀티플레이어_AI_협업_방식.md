# 멀티플레이어 AI 협업 개발 방식

이 문서는 [Claude Academy의 사람·에이전트 팀 원칙](https://academy.claude.com/courses/building-effective-human-agent-teams)을 이 프로젝트에 적용한다. 여기서 멀티플레이어 AI는 게임의 멀티플레이 기능이 아니라, 사람과 AI 에이전트가 목표·작업 현황·산출물을 공유하며 협업하는 방식이다.

## 공동 목표

**2026-11-22까지 사람이 처음부터 끝까지 플레이할 수 있는 AI 직무 성장 시뮬레이션을 완성한다. 생산기술은 5일 완주, NPC 2명, 선택 기억 분기, 행동 근거 보고서까지 구현한다. 두 번째 직무는 같은 엔진에서 대표 미션과 보고서를 실행해 확장성을 확인한다.**

두 번째 직무의 업무 현실성과 NCS 근거는 담당자가 검토하기 전까지 검증 완료로 표시하지 않는다. 실제 능력·채용 적합성 판정은 제품 목표에 포함하지 않는다.

## 팀 명단과 책임

| 담당 | 최종 책임 | 에이전트가 준비 | 사람이 판단·승인 |
|---|---|---|---|
| 1번 | 게임 진행·공통 상태, 직무 목록·로더, 통합 | 구현·테스트·설계 대안 | 상태·API 계약, 게임 흐름 |
| 2번 | NPC 대화·LLM 연결·기억 분리 | 프롬프트·어댑터·대체 응답·테스트 | 모델·비용·데이터 범위, 대사 적절성 |
| 3번 | 직무 미션·행동 근거·평가 보고서 | 콘텐츠 초안·검증 도구·기능 코드 | 업무 사실·NCS 출처·평가 표현 |
| 조율 담당 | 공동 목표·우선순위·일정·충돌 조정 | 진행 요약과 위험·누락 항목 제안 | 범위 변경과 담당자 간 최종 조정 |
| 공유 개발 에이전트 | 담당자가 정한 작업 수행 | 정해진 범위의 코드·문서·테스트 | 범위 밖 또는 고위험 변경은 담당자에게 제안 |

팀은 실제 담당자 이름, 조율 담당자, 리뷰 담당자를 `docs/planning/팀_작업판.md`에 적는다. 모든 작업에는 담당자 한 명(DRI)을 지정한다. 에이전트는 스스로 제품 방향이나 공개 범위를 결정하지 않는다.

## 공용 작업판과 기록

- `docs/planning/팀_작업판.md`: 작업, 담당자, 상태, 브랜치·PR, 다음 행동, 막힌 점을 기록한다.
- `docs/decisions/`: 결정 내용, 이유, 날짜, 결정자와 재검토 조건을 남긴다.
- `docs/contracts/`: 게임 상태, 직무 콘텐츠, API, 행동 근거 형식을 둔다. 계약 변경 PR에는 영향받는 담당자 리뷰를 포함한다.
- 대화나 회의에서 정한 내용은 당일 저장소 기록으로 옮긴다. 에이전트가 다음 작업을 잇는 데 필요한 결과를 대화에만 남기지 않는다.
- 키, 비밀값, 플레이어 식별정보, 개인 대화 원문은 저장소나 공유 메모리에 쓰지 않는다.

## 작업 위임 양식

```text
목표:
담당자(DRI):
에이전트 역할:
입력 문서와 계약:
수정 가능 범위:
완료 조건:
검증 방법:
사람의 결정이 필요한 경계:
산출물 위치와 PR:
```

에이전트는 지정 범위 안에서 코드를 찾아 수정하고 관련 검증을 수행한다. 다른 담당자의 파일이나 공통 계약 변경이 필요하면 먼저 제안한다. 확인되지 않은 업무 사실이나 NCS 코드를 만들어내지 말고 검토 필요로 남긴다. 완료 시 변경 내용, 검증 결과, 남은 문제와 다음 행동을 작업판에 기록한다.

## 자율성을 단계적으로 넓히기

1. 시작 단계에서는 에이전트가 초안과 브랜치를 만들고, 담당자가 매번 변경사항과 검증을 확인한다.
2. 품질이 반복 확인되면 담당자 지정 아래 격리된 기능 구현과 테스트까지 맡긴다.
3. 여러 차례 검증된 저위험 반복 작업은 합의된 규칙에 따라 자동화한다.
4. 제품 범위, 비용, 외부 배포, 비밀·개인정보, 검증되지 않은 평가, `main` 병합은 사람의 판단을 거친다.

신뢰는 작업 종류별로 쌓는다. 한 종류에서 잘 수행했다고 다른 종류의 작업 권한까지 자동으로 넓히지 않는다.

## 팀 작업 리듬

- 매일 작업판에 완료한 일, 오늘 목표, 막힌 점, 결정이 필요한 일을 갱신한다.
- 각 담당자는 기능을 작은 PR로 나누고 다른 담당자의 리뷰와 완료 조건을 포함한다.
- 일반 CI는 가짜 LLM 응답으로 반복 실행한다. 실제 API 품질·속도 확인은 별도로 기록한다.
- 주기 회고에서 반복되는 실수와 누락을 `AGENTS.md`나 검증 절차에 반영한다.
- 통합 완료는 CI 성공과 함께 사람이 대표 사용자 흐름을 실행하고 업무 사실과 결과 표현을 확인한 뒤 판단한다.

## 첫 시작 순서

1. 사람이 조율 담당, 두 번째 직무 후보, 프런트엔드·LLM 선택, 호출 한도와 업무 검토자를 정한다.
2. 에이전트가 공동 목표를 기준으로 작업판, 계약 초안, 직무 데이터 예시와 가짜 테스트 데이터를 만든다.
3. 세 사람이 계약과 두 번째 직무 범위를 함께 확인한다. 합의 전에도 독립 가능한 화면·서비스 초안은 가짜 데이터로 진행한다.
4. 각 담당자가 작업판에서 티켓을 에이전트에 배정하고, 작은 PR을 검토·통합한다. 반복 품질이 확인되면 그 작업의 자율 범위를 조금씩 넓힌다.

기술 구현 세부사항과 담당별 일정은 [3인 상세 개발 계획](3인_상세_개발_계획.md)을 따른다.
