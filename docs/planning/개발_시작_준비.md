# 사람이 먼저 준비할 것과 에이전트 실행 순서

## 사람이 확정할 최소 항목

| 항목 | 사람이 결정·제공할 것 | 에이전트가 준비할 것 |
|---|---|---|
| 제품 범위 | 생산기술 5일 완주 우선, 두 번째 직무 선정, 대상 사용자 확인 | 범위와 제외 항목을 명세로 정리 |
| 업무 현실성 | 실제 업무 사례 1~2개 또는 검토 가능한 현직자 연결 | 사건·선택지·대사 초안과 질문 목록 작성 |
| 기술 선택 | 팀이 유지할 기술과 배포 환경 승인 | React+TypeScript·FastAPI·SQLite 등 후보 검토 및 실행 골격 작성 |
| AI 사용 | API 계정, 모델 사용 권한, 총 예산·호출 제한, 데이터 전송 범위 결정 | 가짜 응답, 호출 제한, 오류 대체 구현 |
| 협업 | 1·2·3번 담당자, 통합 담당자, 리뷰 담당과 병합 권한 지정 | 작업별 브랜치·PR·검증 결과 기록 |
| 결과 표현 | 직무탐색 목적과 평가 한계, 공개 가능한 콘텐츠 승인 | 행동 근거·불확실성 표시 및 검증 |

API 키는 채팅·문서·공유 메모리에 적지 않고 개발 환경이나 배포 환경의 비밀 설정에 넣는다. 키가 없어도 가짜 응답으로 대부분의 개발과 CI를 진행한다. 세부 함수명·화면 코드·폴더를 사람이 일일이 설계할 필요는 없다.

## 에이전트가 초안을 만들고 사람이 한 번 확인할 산출물

1. 사용자 흐름: 직무 선택 → 일정 → 미션·대화 → 다음 날 → 엔딩·보고서.
2. 공통 계약: 게임 상태, 역할 콘텐츠 스키마, API 요청·응답, 행동 기록과 보고서 근거.
3. 대표 시나리오: 생산기술 Day 2 도움/거절이 Day 4에 미치는 차이와 예상 결과.
4. 완료 기준: 5일 완주, NPC 2명, 기억 분기, 근거 연결, API 실패 시 진행, 직무·세션 격리.

이 산출물의 초안 작성과 기술 검증은 에이전트가 수행한다. 사람은 제품 의도·업무 사실·비용·외부 공개 범위를 확인한다. 합의본은 docs/contracts/와 docs/planning/에 저장한다. 아직 해당 계약 파일과 실행 코드는 작성되지 않았다.

## 이후 실행 순서

- 준비 단계: 합의된 계약과 가짜 응답을 만든 뒤 실행 골격을 먼저 통합한다.
- 병렬 단계: 1번 게임 상태·진행, 2번 NPC·기억, 3번 미션·보고서를 각각 구현한다. 같은 작업 디렉터리를 동시에 수정하기보다 별도 worktree와 브랜치를 사용한다.
- 통합 단계: 각 PR에 관련 테스트를 붙이고 다른 담당자가 검토한다. 5일 플레이를 매일 연결해 확인한다.
- 확장 단계: 두 번째 직무를 콘텐츠로 추가하고 공통 엔진에서 실행되는지 확인한다.
- 검수 단계: 사람은 실제 플레이와 업무 현실성을 확인한다. 에이전트는 발견된 오류 수정과 회귀 검증을 반복한다.

## 다시 사람에게 확인할 경계

합의된 범위의 코드·테스트·문서·가짜 데이터 작성은 계속 진행한다. 예산 초과, 유료 서비스 도입, 실제 개인정보 사용, 공개 배포, 기능 범위 확대, 해결되지 않은 업무 사실은 담당자에게 확인한다. PR 병합은 팀에서 정한 권한을 따른다. 확인이 필요한 동안에도 독립적인 개발과 테스트는 계속한다.

## 팀 전달용 시작 지시

“README와 3인 상세 개발 계획, 합의된 계약을 읽고 맡은 기능을 구현하세요. 가짜 응답으로 먼저 연결하고 실제 API는 서버에서만 사용하세요. 관련 테스트를 실행하고 결과와 남은 문제를 PR에 남기세요. 공통 규격 변경은 다른 담당자와 먼저 조율하세요. 비밀값이나 확인되지 않은 NCS 코드를 만들지 마세요.”

현재 미확정: 두 번째 직무, 최종 프런트엔드 기술, LLM 제공자·모델·예산, 배포 환경, 실명 담당자와 업무 검토자. 이 결정이 모두 끝날 때까지 기다릴 필요는 없으며, 에이전트는 계약 초안과 가짜 데이터부터 준비할 수 있다.
