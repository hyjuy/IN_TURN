# 3인 상세 개발 계획

작성일: 2026-11-14 / 목표 완료일: 2026-11-22

기존 역할 분담을 세 명 모두 화면·서버·테스트를 구현하는 기능 단위로 구체화한다. 아래 API·경로·일정은 개발 시작을 위한 제안이며 실제 구현 현황이 아니다. LLM API 사용을 전제로 계획하되 제공자, 모델, 프런트엔드 기술은 아직 미확정이다. 발표자료 제작은 후순위로 둔다.

## 공통 선행 작업 — 11/14~11/15

- 세 명이 프런트엔드 기술, API 제공자, 실행 방법을 결정한다. 별도 모델 학습은 MVP 범위에서 제외하는 제안이다.
- 1번이 게임 상태와 서버 진입점 초안을, 2번이 대화 계약을, 3번이 미션·근거·보고서 계약을 작성한다. 서로 검토하여 `docs/contracts/`에 합의본을 남긴다.
- 게임 상태: session_id, role_id, content_version, version, day, current_event_id, stats, relationships, flags, status.
- 사건·선택: event_id, choice_id, 선행 조건, 허용 선택, 상태 변화, 관련 행동 ID. 규칙은 서버 데이터가 결정한다.
- 행동 기록: action_id, session_id, event_id, action_type, turn, payload. 평가 근거는 해당 기록 ID를 참조한다.
- API 공통: 세션 식별자, 요청 형식, 응답 예제, 잘못된 요청·오래된 상태·존재하지 않는 세션의 오류 형식을 합의한다.
- 세 사람은 응답 예제와 가짜 데이터를 사용해 상대 기능이 완성되기 전에도 개발한다.
- 공통 진입점·DB 연결·상태 변경 함수는 1번이 통합한다. 2·3번은 기능 모듈로 제공하며 공유 파일 수정은 먼저 조율한다.

## 1번 — 게임 진행과 상태

목표: 시작부터 Day 5 종료까지 규칙에 따라 진행하고 저장·재개할 수 있는 게임 골격.

### 구현 순서

1. FastAPI 진입점, SQLite 연결과 세션 저장 모델, 프런트엔드 기본 화면 틀을 만든다. 초기 상태와 완료 상태를 정의한다.
2. 시작·일정·상태 패널을 만들고 세션 생성/조회 API에 연결한다. 새로고침 시 저장된 세션으로 복귀한다.
3. 허용된 선택인지 검증하고 상태 변경과 행동 기록을 한 트랜잭션으로 저장한다. 같은 요청의 중복 반영과 오래된 상태의 선택을 막는다.
4. Day 1 소개와 Day 5 종료 흐름을 작성한다. 2번 대화 화면과 3번 미션 화면을 사건 종류에 따라 연결한다.
5. 엔딩·보고서 진입, 초기화, 잘못된 세션의 복구 안내를 구현한다. 초기화는 해당 세션만 대상으로 한다.

### 제안 작업 위치·API

- `frontend/src/features/game/`, `backend/app/game/`, `backend/app/api/game.py`, `backend/app/models/`, `backend/tests/test_game.py`
- `POST /sessions`, `GET /sessions/{id}`, `POST /sessions/{id}/actions`, `POST /sessions/{id}/reset`
- 상태 변경 함수는 1번이 제공하고 2·3번이 호출한다. 클라이언트나 LLM이 보낸 수치 증감은 그대로 적용하지 않는다.

### 인계·완료 기준

- 11/16까지 초기 상태, 상태 갱신 함수 인터페이스와 응답 예제를 전달한다.
- 정상 진행, 범위 밖 수치, 중복 요청, 허용되지 않은 선택, 저장·재개, 세션별 초기화를 검증한다.
- 대화·미션을 임시 데이터로 대체해도 5일을 끝낼 수 있어야 한다.
- PR 단위: 실행 골격 → 상태·저장 → 화면·5일 진행 → 통합·복구.

## 2번 — NPC 대화와 기억 분기

목표: NPC 두 명이 실제 사건을 기억하고 이전 선택에 맞게 반응하는 경험.

### 구현 순서

1. 상사·선배의 성격, 알고 있는 사실, 말투와 금지 표현을 작성한다. 대화 화면과 가짜 대화 응답부터 연결한다.
2. 서버 전용 LLM 호출 모듈을 만든다. API 키는 환경변수로 주입하고 저장소나 브라우저에 노출하지 않는다.
3. 현재 사건·NPC 설정·관계·관련 행동 기록만 프롬프트에 전달한다. 사용자 대화는 규칙이나 시스템 지시로 취급하지 않는다.
4. 구조화된 응답을 검증한다. 타임아웃, 호출 제한, 잘못된 형식에는 준비된 대사를 사용한다. 호출 횟수와 입력 길이를 제한한다.
5. Day 2 도움/거절 선택과 Day 4 협력/자료 접근 분기를 작성한다. 분기 판정은 서버가 하고 LLM은 판정에 맞는 대사를 생성한다.

### 제안 작업 위치·API

- `frontend/src/features/dialogue/`, `backend/app/api/dialogue.py`, `backend/app/agents/npc.py`, `backend/app/services/llm.py`, `data/roles/<role_id>/characters/`, `data/roles/<role_id>/scenarios/relationships/`
- `POST /sessions/{id}/dialogue`: npc_id, message, event_id를 받고 대사와 대체 응답 사용 여부를 반환한다.
- 관계·플래그 변경은 1번 상태 변경 함수를 거친다. 3번과 Day 2·4 사건 순서를 합의한다.

### 인계·완료 기준

- 11/16까지 대화 응답 예제, 11/17까지 NPC 두 명과 오류 대체 흐름을 제공한다.
- 도움/거절 경로를 각각 재현하고 Day 4 결과가 달라지는지 확인한다.
- 발생하지 않은 사건 회상, 다른 세션 기억 혼입, 긴 입력, API 실패를 검증한다.
- PR 단위: NPC·가짜 대화 → LLM·오류 처리 → 기억·후속 분기.

## 3번 — 업무 미션과 행동 기반 보고서

목표: 업무 행동을 기록하고 확인된 NCS 준거와 연결한 보고서를 보여준다.

### 구현 순서

1. Day 2 생산·불량 자료 확인, Day 3 협업 충돌, Day 4 납기·안전·품질 미션의 자료와 선택지를 작성한다. 2번의 관계 사건과 중복되지 않게 연결한다.
2. 미션 화면과 제출 API를 구현한다. 미션 ID와 허용 답변을 검증하고 1번의 공통 행동 기록 경로를 사용한다.
3. NCS 준거 3~5개의 식별자·원문 출처·이용 조건·검토 상태를 기록한다. 미확인 준거는 평가 보류로 처리한다.
4. 행동 ID → 준거 → 관찰 상태를 규칙으로 연결한다. 관찰됨/근거 부족/관찰 기회 없음을 구분한다.
5. 보고서 API와 화면을 구현한다. 게임 수치와 직무 관찰을 분리하고 각 판단의 행동 근거를 표시한다. AI 문장 생성은 2번 호출 모듈을 재사용하며 실패 시 규칙 기반 문구를 사용한다.

### 제안 작업 위치·API

- `frontend/src/features/missions/`, `frontend/src/features/report/`, `backend/app/api/missions.py`, `backend/app/api/reports.py`, `backend/app/services/evaluation.py`, `data/roles/<role_id>/ncs/`, `data/roles/<role_id>/evaluation/`, `data/roles/<role_id>/scenarios/missions/`
- `GET /sessions/{id}/missions/current`, `POST /sessions/{id}/missions/{mission_id}/submit`, `GET /sessions/{id}/report`
- 보고서 항목: observation_status, action_ids, criterion_id, observation, limitation, next_learning.

### 인계·완료 기준

- 11/16까지 미션·보고서 응답 예제, 11/18까지 미션 3개와 검토된 매핑을 제공한다.
- 기록 없는 판단, 미확인 준거, 다른 세션 근거, 잘못된 제출, 재조회 시 결과 일관성을 검증한다.
- 실제 직무 역량·성격·채용 적합성을 확정하는 문구를 출력하지 않는다.
- PR 단위: 미션·행동 기록 → NCS 매핑 → 보고서·근거 검증.

## PR과 CI

각 기능 PR은 다른 담당자 한 명이 검토한다. 현재 CI는 공백 오류 검사뿐이다. 실행 환경이 생기면 1번이 공통 빌드·테스트 실행을 CI에 연결하고, 2·3번은 각 기능 테스트를 제공한다. 일반 PR 테스트는 가짜 LLM 응답을 사용해 키·과금 없이 재현한다. 실제 API의 대화 품질·속도 검증은 별도로 실행하고 결과를 기록한다.

## 다직무 확장 계획 — 기존 단일 직무 범위를 대체

- 제품은 공통 게임 엔진과 직무별 콘텐츠 묶음으로 구성한다. 직무 수를 코드에 고정하지 않는다.
- MVP는 생산기술 1개의 5일 완주와 두 번째 직무의 짧은 확장 검증을 목표로 한다. 두 번째 직무의 종류는 사람이 선정한다. 검증용 직무를 완성된 5일 콘텐츠로 소개하지 않는다.
- 두 번째 직무는 하나의 미션·NPC 반응·행동 근거 보고서를 같은 엔진에서 실행한다. 신규 게임 규칙을 개발해야 하는 직무는 별도 작업으로 등록한다.
- 공개 목록에는 검토 완료된 직무만 표시한다. draft 콘텐츠는 개발 환경에서만 선택한다.
- 세션 생성 시 role_id와 content_version을 고정한다. 직무 변경은 새 세션으로 시작하며, 기억·행동·평가가 다른 직무나 세션과 섞이지 않게 한다.

### 콘텐츠 구조

`data/roles/<role_id>/` 아래에 manifest.json, characters/, scenarios/, ncs/, evaluation/을 둔다. manifest에는 직무 ID, 이름, 콘텐츠 버전, 검토 상태, 시작 사건을 기록한다. 실제 JSON 스키마는 개발 전 세 명이 합의한다. 기존 data 직하위 폴더는 초기 빈 구조이며 신규 직무 콘텐츠는 roles 아래에 작성한다.

### 담당 추가 업무

- 1번: 직무 목록·선택 화면, GET /roles, role_id를 받는 세션 생성, 직무 콘텐츠 로더, 세션별 버전 고정과 잘못된 직무 차단.
- 2번: 직무별 NPC·배경 로딩과 프롬프트 조립, 직무·세션을 제한한 기억 조회, 두 번째 직무의 대화 검증.
- 3번: 콘텐츠 스키마·참조 무결성 검증, 직무별 미션·준거·보고서 매핑, 두 번째 직무의 샘플 미션. 콘텐츠 작성·준거 조사는 세 명이 분담한다.
- CI에 직무 ID 중복, 사건·선택 참조 누락, 확인되지 않은 준거의 평가 사용, 다른 직무 데이터 혼입을 검사한다. 구현 전에는 검사 완료로 표기하지 않는다.
- 11/16까지 직무를 선택해 임시 콘텐츠를 로딩하고, 11/20에는 두 번째 직무의 미션→대화→보고서를 검증한다. 일정이 지연되면 생산기술 완주를 우선하고 두 번째 직무는 비공개 개발 샘플로 남긴다.
