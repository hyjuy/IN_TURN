# 7일 축소 개발 계획 (제안)

작성일: 2026-11-14 / 개발 기간: 11/15~11/21 (7일) / 예비일: 11/22

**상태: 팀 합의 전 제안이다.** 합의되면 [3인 상세 개발 계획](3인_상세_개발_계획.md)의 범위와 일정을 대체한다. 아래 기술·API·사건 내용은 제안이며 구현 현황이 아니다.

## 왜 줄이는가

- 병목은 코드가 아니라 검증된 직무 콘텐츠다. 개발자 세 명 모두 생산기술 실무를 모른다.
- NCS 문구를 보여주는 것만으로는 NCS 사이트보다 나을 것이 없다. 이 서비스의 가치는 실제 갈등 상황에서 직접 판단해보는 경험이다. NCS는 콘텐츠가 아니라 보고서의 관찰 기준으로만 쓴다.
- 배점이 가장 큰 항목은 AI 활용 적절성(25점)이다. 서버가 모든 것을 정하고 LLM이 대사만 꾸미면 AI가 장식이 된다. 플레이어의 자유 입력을 AI가 해석하는 것을 핵심 기능으로 둔다.
- 그래서 넓이(5일, 2개 직무)를 줄이고 사건 3개의 깊이에 시간을 쓴다.

## 범위

| 항목 | 기존 계획 | 이 계획 |
|---|---|---|
| 게임 길이 | 5일 | 3일, 하루에 사건 1개 (플레이 15~20분) |
| 직무 | 생산기술 + 두 번째 직무 검증 | 생산기술 1개 |
| 플레이어 입력 | 선택지 | 자유 입력(AI 해석) + 선택지 |
| 게임 수치 | 체력·스트레스 등 | NPC 2명과의 관계, 플래그 |
| NCS 준거 | 3~5개 | 3개 |
| 세션 | 저장·재개·초기화, 중복·오래된 요청 방지 | 저장·재개. 초기화는 새 세션 시작으로 대신한다 |
| 협업 기록 | 작업판·결정 기록·계약·위임 양식 | 작업판 1개, 계약 문서 1개, PR |

- **유지**: NPC 2명(상사·선배), 기억 분기 1개, 행동 근거 보고서, LLM 실패 시에도 진행, 서버가 규칙을 결정, 비밀값 규칙, PR 리뷰.
- **제외**: 두 번째 직무, 직무 선택 화면과 `GET /roles`, Day 4~5, 추가 엔딩, 배지, 음향, 자기성찰 에이전트.
- 콘텐츠는 `data/roles/<role_id>/` 아래에 둔다. 직무를 늘리는 코드는 만들지 않지만, 나중에 폴더 추가로 확장할 수 있게 경로만 맞춘다.

## AI가 하는 일

| 기능 | AI가 받는 것 | AI가 내는 것 | 서버가 검증하는 것 | 실패 시 |
|---|---|---|---|---|
| 자유 입력 해석 | 플레이어 문장, 현재 사건의 허용 선택 목록 | 선택 ID 1개 또는 질문 또는 해석 불가, 근거가 된 문장 일부 | 선택 ID가 허용 목록에 있는가 | 선택지 버튼을 보여준다 |
| NPC 대사 | 캐릭터 설정, NPC가 아는 사실, 서버 판정, 관련 행동 기록 | 2~3문장 대사 | 형식, 길이 | 사건별로 준비한 대사를 쓴다 |
| 보고서 문장 | 규칙이 정한 관찰 상태와 행동 기록 | 관찰 내용을 풀어 쓴 문장 | 인용한 행동 ID가 해당 세션에 있는가 | 규칙 기반 문구를 쓴다 |

- LLM은 상태를 바꾸지 않는다. 상태 변경은 검증된 선택 ID를 받은 서버만 한다.
- 플레이어 문장은 데이터로만 다루고 시스템 지시로 취급하지 않는다. 입력은 300자로 제한한다.
- NPC는 "아는 사실" 목록 밖의 직무 지식을 말하지 않는다. 전문성은 모델이 아니라 콘텐츠에서 나온다.
- 기억은 대화 원문이 아니라 행동 기록에서 온다. 현재 사건과 관련된 기록만 프롬프트에 넣는다. 벡터 DB나 캐시는 쓰지 않는다.
- 호출은 플레이 한 번에 약 50회 이내로 제한한다(사건당 질문 5회). 실제 호출 수와 비용은 11/20에 측정해 기록한다.

## 한 턴의 흐름

1. 화면에 사건 자료와 NPC 대사를 보여준다.
2. 플레이어가 문장을 쓰거나 선택지 버튼을 누른다.
3. 문장을 썼다면 AI가 해석하고 "이렇게 이해했습니다: …"를 보여준다. 플레이어가 확인하거나, 다시 쓰거나, 버튼에서 고른다.
4. 서버가 선택을 검증하고 상태 변경과 행동 기록을 한 트랜잭션으로 저장한 뒤 NPC 대사를 만든다.
5. 문장이 질문이면 NPC가 아는 사실 안에서 답하고, 질문도 행동으로 기록한다.
6. 사건이 끝나면 다음 날로 넘어가고, Day 3이 끝나면 보고서를 보여준다.

## 사건 3개

아래는 기존 문서의 주제를 옮긴 가설이며 **현직자 검토 전**이다. 실제 사례를 구하면 교체한다.

| 날 | 사건 | 핵심 판단 | 기억 연결 |
|---|---|---|---|
| Day 1 | 불량 자료 확인 과제 중 선배가 자기 업무를 도와달라고 한다 | 무엇을 먼저 확인하는가, 돕는가 거절하는가 | 도움/거절을 플래그로 남긴다 |
| Day 2 | 공정 조건 변경을 두고 생산 현장과 의견이 갈린다 | 누구에게 무엇을 근거로 말하는가 | 상사와의 관계에 반영한다 |
| Day 3 | 납기가 임박했는데 불량이 의심된다 | 출하, 보류, 보고 중 무엇을 하는가 | Day 1 선택에 따라 선배의 협조와 자료 접근이 달라진다 |

### 콘텐츠 확보

- 현직자 1명을 섭외해 11/17까지 30분 인터뷰한다. 생산기술이 아니어도 품질·생산관리 등 인접 직무면 된다.
- 물을 것: 신입이 첫 달에 실제로 받는 일, 가장 흔한 실수, 납기와 품질이 부딪힌 실제 상황, 그때 누구에게 무엇을 보고하는가, 위 사건 3개에서 현실과 다른 부분.
- 인터뷰 전에는 공개된 품질·안전 사례와 현직자 직무 인터뷰 자료로 초안을 쓴다. 출처와 이용 조건을 `docs/research/`에 기록한다.
- 11/17까지 인터뷰하지 못하면 공개 자료 기반으로 진행하고, 화면과 보고서에 "현직자 검토 전"을 표시한다.
- NCS 준거 3개의 식별자·원문·출처는 사람이 NCS 사이트에서 직접 확인한다. 확인되지 않은 준거는 평가 보류로 처리하고, 에이전트는 코드를 만들어내지 않는다.

## 기술 (제안, 11/14 확정 필요)

- 서버: FastAPI, SQLite. 테이블은 세션(상태 JSON)과 행동 기록 2개.
- 화면: React + Vite. 팀이 더 익숙한 것이 있으면 그것을 쓴다.
- LLM: 제공자 1개, 소형 모델 우선. 함수는 해석·대사·보고서 문장 3개이며 각각 가짜 구현을 둔다.
- 실행: 로컬 실행과 시연 영상을 기본으로 한다. 공개 배포는 예선 제출 요건을 확인한 뒤 결정한다.

## 계약 요약

합의본은 `docs/contracts/`에 문서 1개로 둔다.

- 게임 상태: session_id, role_id, content_version, day, current_event_id, relationships, flags, status.
- 행동 기록: action_id, session_id, event_id, action_type(choice/question), choice_id, source(button/free_text), text.
- API:
  - `POST /sessions`: 세션을 만들고 상태를 반환한다.
  - `GET /sessions/{id}`: 상태와 현재 사건(자료, 선택지)을 반환한다.
  - `POST /sessions/{id}/interpret`: 문장을 해석한다. 상태를 바꾸지 않는다.
  - `POST /sessions/{id}/actions`: 선택 또는 질문을 반영하고 새 상태와 NPC 대사를 반환한다.
  - `GET /sessions/{id}/report`: 보고서를 반환한다.
- 요청의 event_id가 current_event_id와 다르면 거절한다. 중복·오래된 요청은 이것으로 막는다.
- 보고서 항목: criterion_id, observation_status(관찰됨/근거 부족/관찰 기회 없음), action_ids, observation, limitation.

## 담당

기존 분담의 축(1번 진행·상태, 2번 NPC·LLM, 3번 미션·보고서)은 유지하고 두 가지를 바꾼다.

- **보고서 화면을 3번에서 1번으로 옮긴다.** 범위를 줄이면서 1번의 일이 가장 많이 줄었고, 3번은 일정의 병목인 콘텐츠 확보에 시간을 써야 한다.
- **3번은 화면을 만들지 않는다.** "세 명 모두 화면·서버·테스트를 구현한다"는 기존 원칙의 예외다.

### 1번 — 진행·상태·통합

- 맞는 사람: 서버와 화면을 모두 다뤄본 사람.
- 서버: 실행 골격, 세션 저장·재개, 사건 로더, `actions`의 선택 검증과 트랜잭션, 플래그 조건에 따른 분기 판정, 날짜 전환.
- 화면: 시작 화면, 플레이 화면의 틀(사건 자료·선택지 버튼·관계 표시), 보고서 화면.
- 공통: 2·3번 모듈 연결, CI에 테스트 실행 추가, 실행 안내 작성.
- 콘텐츠: Day 2 사건의 자료·선택지·규칙 초안.
- 위치(제안): `backend/app/main.py`, `backend/app/game/`, `backend/app/models/`, `backend/app/api/sessions.py`, `frontend/src/features/game/`, `frontend/src/features/report/`.
- PR 단위: 실행 골격 → 상태·저장·로더 → 3일 진행 → 보고서 화면.

### 2번 — AI 모듈과 NPC

- 맞는 사람: LLM API를 써본 사람.
- 서버: LLM 호출 모듈과 가짜 구현, 자유 입력 해석(`interpret`), NPC 대사, 질문 응답, 형식 검증·타임아웃·대체 대사, 보고서 문장 함수.
- 화면: 플레이 화면 안의 대화 패널(대사 목록, 입력창, "이렇게 이해했습니다" 확인).
- 콘텐츠: 상사·선배 캐릭터 설정(성격, 말투, 금지 표현), 사건별 NPC가 아는 사실, 사건별 준비 대사.
- 검증: 해석 평가셋 측정, 실제 API로 환각 회상·호출 수·비용 기록.
- 위치(제안): `backend/app/services/llm.py`, `backend/app/agents/`, `backend/app/api/interpret.py`, `frontend/src/features/dialogue/`, `data/roles/<role_id>/characters/`.
- PR 단위: 가짜 응답과 대화 패널 → 실제 해석·대사·대체 → 질문 응답과 기억 분기 대사.

### 3번 — 콘텐츠와 평가

- 맞는 사람: 사람을 만나 묻고 글로 정리하는 일을 잘하는 사람. 제조업 인맥이 있으면 가장 좋다.
- 콘텐츠: 현직자 섭외·인터뷰·검토 창구, Day 1·Day 3 사건의 자료·선택지·규칙, 1번이 쓴 Day 2 검토, 사건 3개의 일관성.
- 평가: NCS 준거 3개의 원문·출처·이용 조건 확인, 행동→준거 규칙, 관찰 상태 판정, 한계 문구.
- 서버: 보고서 API, 콘텐츠 참조 검사 테스트(사건·선택·준거 참조 누락, 미확인 준거의 평가 사용).
- 기록: 출처와 인터뷰 요약을 `docs/research/`에 남긴다.
- 위치(제안): `data/roles/<role_id>/scenarios/`, `data/roles/<role_id>/ncs/`, `data/roles/<role_id>/evaluation/`, `backend/app/services/evaluation.py`, `backend/app/api/reports.py`.
- PR 단위: 사건 1 데이터와 참조 검사 → 사건 2·3과 인터뷰 반영 → 준거 규칙과 보고서 API.

### 경계

| 지점 | 제공 | 사용 | 약속 |
|---|---|---|---|
| 상태 변경 | 1번 | 2·3번 | 상태는 1번의 함수로만 바꾼다. 2·3번은 직접 저장하지 않는다 |
| 현재 사건과 허용 선택 | 1번 로더 | 2번 해석 | 해석 결과는 이 목록 안의 선택 ID여야 한다 |
| 대화 패널 → 선택 제출 | 2번 패널 | 1번 화면 | 패널은 확인된 선택 ID를 넘기고, 제출은 1번 코드가 한다 |
| NPC 대사 | 2번 함수 | 1번 `actions` | 판정과 관련 행동 기록을 받아 대사를 돌려준다. 실패하면 준비 대사를 준다 |
| 행동 기록 조회 | 1번 | 3번 보고서 | 세션 ID로만 조회한다 |
| 보고서 응답 | 3번 API | 1번 화면 | 11/15의 응답 예제를 기준으로 화면을 만든다 |
| 보고서 문장 | 2번 함수 | 3번 API | 선택 사항이다. 없으면 규칙 기반 문구를 쓴다 |

- 분기는 판정과 대사로 나눈다. Day 3에서 선배가 협조하는지는 사건 데이터의 조건과 1번의 엔진이 정하고, 2번은 그 판정에 맞는 대사를 만든다.
- 해석 평가셋 30문장은 세 명이 10문장씩 쓴다. 2번 혼자 쓰면 자기 프롬프트에 맞는 말투만 모인다.
- 리뷰: 1번 PR은 2번이, 2번 PR은 3번이, 3번 PR은 1번이 본다. 계약 변경은 세 명이 모두 본다.
- 기획안 사본은 원본을 가진 사람이 11/15까지 `docs/planning/`에 넣는다.

## 완료 기준

- LLM을 꺼도 버튼만으로 3일을 완주한다.
- Day 1의 도움/거절에 따라 Day 3의 결과와 선배의 대사가 달라지는 것을 두 경로 모두 재현한다.
- 해석 평가셋 30문장의 일치율과 오분류 사례를 기록한다. 목표 수치는 첫 측정 후 정한다.
- 실제 API로 10회 플레이하여 일어나지 않은 사건을 회상한 사례를 세고 기록한다.
- 보고서의 모든 판단이 행동 ID를 참조하고, 실제 역량·채용 적합성을 확정하는 문구가 없다.
- 일반 테스트는 가짜 LLM으로 키 없이 통과한다.

## 늦어질 때 줄이는 순서

1. 보고서 AI 문장을 규칙 기반 문구로 바꾼다.
2. NPC 질문 응답을 사건별로 준비한 답변으로 바꾼다.
3. 사건을 2개로 줄이고 기억 분기를 Day 1 → Day 2로 옮긴다.

자유 입력 해석, 기억 분기 1개, 행동 근거 보고서, 완주는 끝까지 유지한다.
