# Pull Request 협업 기준

## 작업 시작

- `main`에서 작업별 브랜치를 만든다. 이름은 `feature/작업명`, `fix/작업명`, `docs/작업명`을 사용한다.
- 공유 작업 상태에 담당자, 에이전트(사용한 경우), 브랜치, 작업 범위를 기록한다. GitHub 계정은 커밋 작성자를 나타내며 에이전트 구분은 작업 기록에 남긴다.
- 같은 파일이나 API·게임 상태 규격을 수정할 때는 담당자끼리 먼저 조율한다.

## PR 생성 기준

- 하나의 PR은 하나의 목적을 다룬다. 독립적인 기능이나 수정은 별도 PR로 나눈다.
- 검토할 수 있는 변경이 준비되면 PR을 올린다. 미완성이거나 피드백이 먼저 필요하면 Draft로 표시한다.
- 제목은 `feat:`, `fix:`, `docs:`, `refactor:`, `test:` 등으로 시작하고 변경 내용을 구체적으로 쓴다.
- PR 본문에 변경 목적과 내용, 확인 방법과 결과, 남은 문제를 적는다. 화면 변경은 가능하면 스크린샷을 첨부한다.
- API, 게임 상태 또는 데이터 형식이 바뀌면 관련 계약 문서와 영향을 받는 사용처를 함께 갱신한다.
- 비밀키, 토큰, 개인정보 및 사용 허가가 확인되지 않은 자료를 포함하지 않는다.

## 검토 및 병합 기준

- 작성자는 관련된 가장 작은 테스트·검증을 실행하고 결과를 기록한다. 실행하지 못했다면 이유와 영향을 명시한다.
- 리뷰어는 요구사항, 오류 가능성, 기존 기능 영향, 데이터·보안 위험 및 검증 결과를 확인한다. AI가 작성한 변경도 같은 기준으로 검토한다.
- 가능한 경우 작성자가 아닌 팀원 1명 이상이 승인한다. 긴급 상황 등으로 불가능하면 이유와 후속 검토 담당자를 PR에 기록한다.
- 충돌과 필수 검사 실패, 해결되지 않은 필수 리뷰를 처리한 뒤 병합한다. 적용된 브랜치 보호 규칙이 있으면 이를 따른다.
- 병합 후 공유 작업 상태에 결과와 남은 문제를 기록한다. 배포는 별도 승인 또는 명시적 요청에 따라 진행한다.
